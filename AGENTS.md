# Инструкции для агентов

Репозиторий содержит самостоятельный мод TDF / MDC для Hearts of Iron IV. `mdredux/` — историческое имя каталога исходников и не указывает на принадлежность к другому моду. Wiki по коду находится в `wiki/`, исследования — в `docs/research/`. Не использовать код, репозитории, справочники или upstream другого мода как подтверждение механик TDF. Отсутствующее определение остаётся неизвестным, пока оно не найдено в исходниках TDF или в файле целевой сборки, который предоставил пользователь. Для модификаторов, эффектов и триггеров сначала проверять [вики MDC](https://github.com/minusleto/MDC); если там нет нужного определения или его поведения, запрашивать соответствующий файл у пользователя.

Перед работой с контентом страны прочитать `skills/tdf-country-content/SKILL.md`: в нём маршрутизация к справочникам. Открывать только нужные строки таблицы, файлы больше ~100 строк читать по разделам (`grep -n '^#'`, затем нужный диапазон). `skills/tdf-country-content/references/README.md` (карта источников правды) открывать только при конфликте правил. Для тега с карточкой открывать только `references/countries/<TAG>.md`, не весь каталог: карточка — контекст, не шаблон и не историческая верификация. `design-guide.md` нужен только для проектирования или ревью целой ветки.

Главное:
- Фокус по возможности открывает инструмент (решение, дух-ключ, событие с выбором, механику), а не только выдаёт числа. Мосты допустимы, если связывают этапы ветки.
- Длина описания фокуса: редакторский ориентир 200–280 знаков, допустимый диапазон 150–340. Не ломать хороший текст ради счётчика; главное — конкретика, естественность и соответствие награде.
- Не назначать одну страну универсальным эталоном. Для фокусов, событий и опций выбирать подходящие примеры из разных стран и переносить только те приёмы, которые работают в конкретном контексте. Подписи вроде `Nice/Good/Excellent` оценивать по смыслу события, а не запрещать автоматически.
- Картинка события желательна, но не обязательна: не ставить неподходящий GFX ради заполнения поля. Плейсхолдер — только с `#TODO`.
- Описанное в тексте должно соответствовать реальной награде; `log` должен соответствовать ID. В новых и редактируемых блоках соблюдать табы и соглашения проекта, но не форматировать массово нетронутый legacy-контент. Для yml сохранять UTF-8 BOM и исходные окончания строк.
- Аудит — статическая проверка, не тест игры. Из корня репозитория запускать `python3 -I skills/tdf-country-content/scripts/tdf_audit.py . --require-external-registry` и `python3 -I skills/tdf-country-content/scripts/tdf_inventory.py .`; для быстрой проверки без шума использовать `python3 -I skills/tdf-country-content/scripts/tdf_baseline.py check` (только новые находки относительно `docs/research/audit-baseline.json`, который не читать целиком); external references, source permalinks и verification statuses вести в `docs/research/external-dependencies.json` и пояснять в соседнем `.md`.
- Куда заливать: мелкие и средние правки (до ~10 файлов и ~300 строк: контент одной страны, тексты, документация) сразу в `main`. Перед пушем сверить актуальный HEAD (не перезаписывать чужие коммиты) и локально прогнать тесты и `tdf_baseline.py check`: CI в этом случае сработает уже после попадания в `main`. Крупные изменения идут через PR: всё, что меняет `skills/**/scripts/`, тесты, `.github/` или `docs/research/audit-baseline.json`, а также правки больше ~10 файлов или ~300 строк и массовые рефакторинги.
- Отправка через PR одной командой (ветка с коммитами, `GH_TOKEN` в окружении): `python3 -I skills/tdf-country-content/scripts/tdf_ship.py --title "..."`. Скрипт пушит ветку, открывает PR, ждёт CI, при зелёном сливает и печатает одну строку итога; `--dry-run` проверяет условия, `--no-merge` оставляет слияние человеку.

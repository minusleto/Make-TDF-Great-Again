# Решения TDF/MDC: устройство, проектирование и проверка

Этот документ — действующий проектный справочник по решениям. Это не шаблон, которому обязана соответствовать каждая страна: количество категорий, частота повторения, цена, длительность и наличие отдельных полей зависят от механики.

## 1. Текущий состав репозитория

Срез mdredux/common/decisions/ на 24.11.2026:

| Файл | Категорий | Решений |
|---|---:|---:|
| Belarus.txt | 6 | 62 |
| United Kingdom.txt | 4 | 64 |
| Georgia.txt | 1 | 29 |
| Israel.txt | 7 | 53 |
| Russia.txt | 2 | 44 |
| hungary.txt | 5 | 27 |
| **Всего** | **25** | **279** |

Подсчёт — число непосредственных блоков категорий и непосредственных блоков решений внутри них в текущих файлах. Это структурная статистика, а не число одновременно доступных решений в игре. Динамические категории, определения из базового MD и runtime-условия в эти числа не входят.

Отсутствие файла решений у страны само по себе не является проблемой. Решения не обязаны присутствовать в каждом country pack, а число категорий не нужно выравнивать между странами.

## 2. Когда использовать focus, decision, event и national spirit

| Элемент | Основная роль | Типичный жизненный цикл |
|---|---|---|
| Focus | Плановый шаг стратегической ветки, открывает или меняет систему | Обычно одноразовое прохождение ветки |
| Decision | Действие игрока внутри уже открытой системы: вложение, операция, реформа, дипломатический шаг | Одноразовое, повторяемое, с cooldown или timed-этапом |
| Event | Реакция, выбор, уведомление или следующий эпизод цепочки | Вызов по условию/событию; может передавать ход другой стране |
| National spirit / idea | Постоянное или временное состояние страны, которое читают фокусы, решения и другие системы | Пока не снят, не заменён или не истёк таймер |

Хорошая композиция часто выглядит так: focus открывает категорию/инструмент; decision даёт игроку повторяемое или целевое действие; event сообщает результат или предлагает ответ; idea/flag/variable сохраняет состояние, которое открывает следующий шаг.

Не превращай всякое действие в decision. Если это обязательная одноразовая развилка с большим сюжетным выбором — может лучше подойти event. Если действие — центральный стратегический этап ветки — может лучше подойти focus. Если результат должен постоянно влиять на страну — это состояние в idea/modifier, а не текст кнопки.

## 3. Категория решений

В текущих файлах категория обычно задаётся как верхнеуровневый блок, внутри которого лежат блоки решений:

~~~hoi4
KAZ_category = {
    KAZ_example_decision = {
        # decision fields
    }
}
~~~

Категория группирует связанные действия и может иметь собственные условия и параметры. Встречаются allowed, visible, icon, priority и иные UI/visibility-настройки. Не копируй все поля в каждую категорию механически.

**Родительские условия категории применяются ко всем вложенным решениям.** В HOI4 соответствующие gates категории и конкретного решения должны быть выполнены совместно: решение не появится/не станет доступным, если фильтр категории не пройден, даже когда у самого решения свой блок отсутствует. Поэтому если вся категория предназначена только для исходной страны SOV, достаточно одного `allowed = { original_tag = SOV }` на уровне категории. Не дублируй тот же `allowed` в каждом дочернем решении. У решения оставляй собственный `allowed` только для дополнительного статического ограничения, более узкого, чем фильтр категории. Это совместные ограничения (AND), а не замена родительского фильтра дочерним.

```hoi4
SOV_category = {
    allowed = { original_tag = SOV }

    SOV_general_decision = {
        # Отдельный allowed не нужен: parent category gate уже ограничивает страну.
        visible = { has_country_flag = SOV_general_unlocked }
    }

    SOV_special_decision = {
        # Дополнительный фильтр нужен только если этот шаг ограничен ещё сильнее.
        allowed = { has_country_flag = SOV_special_system_enabled }
        visible = { has_country_flag = SOV_special_unlocked }
    }
}
```

`allowed` — статический фильтр, проверяемый при старте игры/загрузке сохранения. Используй для `original_tag`, DLC и других условий, которые не должны динамически меняться в ходе партии. Для динамических условий применяй `visible` и `available` на соответствующем уровне. Если сама категория должна появляться/исчезать динамически, используй её `visible`; для состояния конкретной кнопки — `visible`/`available` решения.

Разделяй назначение условий:

- allowed — фильтр применимости категории/решения. Фильтр категории действует на все вложенные решения; одинаковое условие категории и её решений не дублируй. Собственный allowed решения добавляй только как дополнительное, более узкое ограничение. При отсутствии собственного allowed у решения остаётся только родительский gate. В стандартном HOI4 allowed проверяется при старте игры/загрузке сохранения; не клади туда условия, которые должны динамически открывать/закрывать решение во время партии.
- visible — показывает ли решение игроку. Если условие ложно, решение скрыто.
- available — можно ли нажать решение сейчас. Не используй его вместо visible, когда нужно скрыть недоступный игроку сюжет/механику.
- priority, icon, picture, visible_when_empty, collapse и похожие атрибуты — оформление и порядок отображения; конкретную поддержку проверяй в используемой версии HOI4/MD.

Категория должна помогать игроку понять, к какой системе относится действие. Не создавай отдельную категорию на каждую кнопку, если они принадлежат одной механике.

## 4. Поля решения и жизненный цикл

### Базовые условия и интерфейс

- icon — иконка кнопки. Используй существующий подходящий GFX/иконку, не придумывай новые имена ресурсов.
- allowed — фильтр применимости; динамическое условие обычно размещай в visible или available.
- visible — условие появления в списке.
- available — условие доступности нажатия.
- ai_will_do — вес выбора AI. Смотри на base, factor, add и вложенные modifier; по умолчанию AI не выбирает обычные decisions, если не задан ai_will_do.
- priority и поля категории — интерфейсная группировка, а не игровая награда.

visible и available могут использовать одинаковые условия, если действие должно пропадать из списка при невыполнимости. Если нужно показать игроку заблокированную кнопку, условие чаще размещается в available, а более широкое условие — в visible. allowed, visible и available нельзя считать взаимозаменяемыми.

Отдельный случай — **автоматически запускаемая decision mission/ticker** с `activation` и `days_mission_timeout`. У неё `available = { always = no }` может быть намеренным: миссия появляется/запускается по `activation`, а не по нажатию игрока; дальше работают `cancel_trigger`, `timeout_effect` и другие mission-поля. Не объявляй её недостижимой только из-за запрета ручного выбора: проследи источник активации и завершение. Обычное решение без пары `activation` + `days_mission_timeout` с `available = { always = no }` остаётся кандидатом на проверку. `allowed = { always = no }` — отдельный случай: он блокирует решение при старте/загрузке, поэтому сохраняется как review candidate даже у mission-блока.

Аудитор дополнительно формирует WARN-only кандидаты на прямое противоречие между обязательными атомарными предикатами в visible и available. Он распознаёт простые условия, раскрывает AND и ограниченно обрабатывает NOT/NOR; дочерние условия OR не считаются обязательными. Сложные отрицания, scripted triggers, динамические scope и общая логическая выполнимость не вычисляются. allowed намеренно не сравнивается с этими динамическими gate: это отдельный фильтр применимости. Любой кандидат требует ручной проверки и не повышает exit code.

### Стоимость

- cost — стандартная стоимость решения в политической силе. Значение должно быть числом; оценивай его вместе с экономическим положением страны и частотой нажатий.
- custom_cost_trigger — проверка наличия нестандартного ресурса/условия для кнопки.
- custom_cost_text — ключ локализации, объясняющий нестандартную стоимость.

**Критически важно:** custom_cost_trigger и custom_cost_text сами по себе не списывают ресурс. Фактическое списание нужно сделать эффектом — обычно в complete_effect, либо в другом сознательно выбранном этапе. Для казны TDF часто используется связка set_temp_variable = { treasury_change = -N } + modify_treasury_effect = yes; для command power, техники, переменных и иных ресурсов — соответствующий расходующий эффект. Если оставить только trigger и надпись, игрок может получить действие без реального списания.

Не задавай одновременно cost и custom cost без ясной причины: UI и ожидания AI могут разойтись. Если нестандартная цена выражена через PP, предусмотренный движком ai_hint_pp_cost может сообщить AI примерную стоимость; проверяй поддержку и точный смысл для своей версии.

Аудитор ищет частые шаблоны списания ресурсов, но не может доказать, что любой динамический расход реализован правильно. Списания через scripted effect, кастомную функцию или сложную переменную нужно проверять вручную.

### Таймер, повторное использование и эффекты

- fire_only_once = yes — одноразовое решение. Не добавляй days_re_enable как будто он делает такое решение повторяемым.
- days_remove = N — длительность активного/timed-состояния решения после выбора. days_remove = -1 используется для бессрочного ожидания/миссии; снятие может зависеть от отдельного trigger.
- complete_effect выполняется при выборе решения и обычно запускает действие/таймер.
- remove_effect выполняется, когда timed-решение удаляется по окончании срока или предусмотренному условию. Не путай его с complete_effect.
- days_re_enable = N задаёт задержку до повторной доступности после завершения/удаления решения. Смотри на него вместе с days_remove, fire_only_once, флагами и условиями: решение не должно случайно появляться слишком часто или исчезать навсегда.
- remove_trigger может завершать timed-решение при выполнении условия; cancel_trigger/cancel_effect могут отменять его без обычного remove_effect, если такая логика поддерживается используемой версией.
- modifier и targeted_modifier подходят, когда решение должно поддерживать временный эффект во время своего активного периода; проверь, что окончание timed-этапа действительно снимает ожидаемое состояние.

Не все решения обязаны иметь таймер. Для мгновенного действия обычно достаточно complete_effect и fire_only_once либо cooldown. Для долгой операции используй timed-модель только тогда, когда время и промежуточное состояние имеют смысл.

### География и целевые решения

В текущих файлах встречаются highlight_states, highlight_state_targets, highlight_states_trigger, highlight_provinces, target_array и on_map_mode.

- highlight_states подсказывает игроку географию действия. Сверяй подсвечиваемые state IDs с теми же территориями, которые проверяются и изменяются в available/complete_effect.
- Разделяй владение, контроль, core и subject status. owns_state не равно controls_state/has_full_control_of_state.
- Если решение использует соседей, массивы или список target countries, явно определяй, кто является ROOT, FROM и фактическим target.
- target_array и on_map_mode используй только когда действие действительно выбирает цель. Не добавляй map-поля ради оформления обычной кнопки.

В текущем checkout нет файлов history/states ни в mdredux/history/states, ни в mdredux/common/history/states. Поэтому локальный статический аудит может проверить, что state в highlight — числовой ID, но не может подтвердить существование каждого state. Такие IDs нужно сверять с полной установленной базой MD/HOI4 или в игре; отсутствие state-файла в этом репозитории не является ошибкой.

## 5. Открытие и межфайловые зависимости

Решение нередко является продолжением другой системы:

- focus открывает категорию/решение через has_completed_focus, идею или флаг;
- idea может открывать категорию через has_idea или быть ступенью/результатом решения;
- event может запускаться из complete_effect/remove_effect и передавать ответ другой стране;
- флаги, переменные и массивы удерживают этап операции и читаются следующими решениями/событиями;
- scripted effects выносят повторяемую механику; при ссылке нужно проверить, что эффект существует в доступной части мода;
- has_decision и родственные triggers ссылаются на решение, которое должно реально существовать.

Для каждого такого перехода проверь ID и scope. Условия, эффекты и tooltip должны описывать одно и то же действие. Не дублируй бонус в focus и decision, если игрок может получить его дважды.

### 5.1. Сверка обещания игроку с фактическим эффектом

Это смысловая проверка, а не подсчёт ключевых слов. Для каждой decision option и каждого materially значимого результата сопоставь текст игрока с исполняемой веткой:

1. **Запиши утверждение текста.** Что именно обещано: списание ресурса, получение техники/духа/технологии, контроль территории, запуск проекта, изменение отношений, событие партнёру, случайный исход или срок.
2. **Найди исполняемую реализацию.** Проверь полный путь от выбора до результата: `complete_effect`, timed decision и `remove_effect`, timeout/cancel, отправляемые события и выбранный option, затем все вызываемые scripted effects. Не останавливайся на первом wrapper-вызове.
3. **Отдели исполнение от подсказки.** `effect_tooltip`, `custom_effect_tooltip`, `custom_cost_text` и текст локализации сами по себе не выполняют эффект и не списывают ресурс. Если эффект показан в tooltip, найди отдельное реальное действие в соответствующей ветке.
4. **Сверь ресурс и величину.** Сравни cost/custom-cost gate, показанную стоимость и фактический debit: один ресурс, одинаковое количество и единицы. Проверь знак, временную переменную, округление и то, что списание происходит ровно один раз.
5. **Сверь scope и момент.** Уточни, кто получает результат (ROOT/FROM/инициатор/партнёр/штат), когда он применяется и сохраняется ли после окончания таймера. Проверь, что условие и эффект относятся к одной цели.
6. **Пройди все исходы.** Отказ, согласие, случайные ветки, timeout, повторный запуск и AI не должны обещать одинаковую награду, если фактически дают разные результаты.
7. **Сверь текст с числами и ограничениями.** Убедись, что описание не обещает больше единиц, более ранний срок, постоянный эффект или гарантированный успех, чем реально выдаёт код.

Для короткого ревью используй таблицу; одна строка — одно проверяемое обещание, а не весь текст целиком:

| Обещание игроку | Реальный эффект / ветка | Scope и момент | Совпадает? / причина |
|---|---|---|---|
| Например: «получить 12 машин после согласия» | Событие согласия → stockpile grant 12; отказ не выдаёт | Получатель, после ответа | Да / нет + ссылка на файл и строку |

Если реализация внешняя, не найдена в доступном checkout или зависит от базового MD/DLC, ставь `unknown/external` и указывай, что именно нужно проверить. Не объявляй обещание ложным только потому, что локальный поиск не раскрыл внешний scripted effect. Аудитор помогает найти ссылки и структуру, но смысловое совпадение подтверждает reviewer.

Проверка аудитора различает:
- local missing — ссылка ведёт на ID с локальным namespace/префиксом, но определения нет в текущем checkout;
- external — namespace/префикс не найден в этом срезе; ID может быть определён базовым MD или другим модулем;
- candidate — автоматическая проверка не может доказать ошибку (например, флаг мог быть установлен через внешний scripted effect).

## 6. Локализация

Аудитор просматривает все mdredux/localisation/english/*.yml, а не только MD_decisions_l_english.yml: в TDF названия и описания конкретных решений часто хранятся рядом со страновой локализацией.

- Ключ заголовка категории — ID категории.
- Ключ названия решения — ID решения.
- Ключи _desc необязательны, если отдельное описание не задумано; если они добавлены, проверь их текст и все scripted-localisation ссылки внутри.
- custom_cost_text, custom_effect_tooltip и custom_trigger_tooltip должны указывать на понятный игроку текст. Общие ключи могут находиться вне локального среза; аудитор разделяет локальные и внешние кандидаты.
- Условия и эффекты должны совпадать с текстом стоимости и результата. Не обещай расход, бонус или последствие, которого нет в эффекте.

## 7. AI и баланс

ai_will_do нужен, когда необходимо управлять частотой выбора AI. Не задавай высокий base всем решениям: AI может повторять действие, которое полезно игроку только один раз или требует ручного выбора. Учитывай visible, available, cooldown, текущую войну, бюджет, нужду в ресурсах и ожидаемый результат.

Цена должна быть соразмерна:
- регулярности действия и cooldown;
- доступному доходу/казне, долгу и экономическим законам страны;
- ценности результата (инфраструктура, армия, дипломатическое влияние, смена закона);
- возможностям AI и тому, будет ли он пытаться выполнить действие без сохранения ресурсов.

Не существует универсальной цены или числа решений. Сверяй с экономикой страны и тестируй на реальной скорости игры, а не только по текстовому числу.

## 8. Проверка через tdf_audit.py

Общий аудитор дополняет ручное ревью следующими проверками:

- дубли ID категорий и решений, синтаксические ошибки и некорректные числовые cost/таймеры;
- локализация названий категорий/решений и локальных tooltip/cost keys;
- has_decision, has_completed_focus, ссылки на события и идеи;
- кандидаты на неразрешённые country flags и scripted localisation;
- custom cost без очевидного расходующего эффекта, cost вместе с custom cost, парность custom_cost_trigger/custom_cost_text;
- подозрительное сочетание fire_only_once и days_re_enable, пустые effect blocks, постоянно ложные always = no условия;
- WARN-only кандидаты на противоположные обязательные атомарные предикаты между visible и available (без полного решения OR/scope/scripted logic);
- числовой формат highlight-state IDs и сверка с state inventory, только если state files действительно присутствуют в checkout.

ERROR — доказуемая структурная проблема или отсутствующая локальная ссылка. WARN — кандидат на ручную проверку, в том числе когда эффект расхода спрятан в scripted effect или ссылка может быть внешней. Повтор category ID в нескольких файлах выводится как кандидат на проверку, поскольку разные файлы могут расширять одну категорию; повтор category в одном файле и повтор decision ID считаются ошибками. Ни одно предупреждение о стоимости, условии, флаге, балансе или AI не является автоматическим доказательством ошибки. Отсутствие локального state inventory явно отмечается: неизвестный state ID не объявляется отсутствующим.
